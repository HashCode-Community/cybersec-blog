NIVEAU : AVANCÉ

Exploitation web : injections SQL et XSS

Objectif : provoquer puis corriger les deux vulnérabilités web les plus enseignées — l'injection SQL et le cross-site scripting (XSS). Tout se passe dans une machine virtuelle isolée, sur une application volontairement vulnérable.

DURÉE 90 minutes
OUTILS DVWA ou OWASP Juice Shop, navigateur, Burp Suite Community
PRÉREQUIS Article « Comprendre les ports réseau » + notions HTTP

⚠ Cadre de l'exercice

À lire avant de commencer : ce laboratoire se déroule exclusivement sur une machine virtuelle isolée, sur une application volontairement vulnérable que tu installes toi-même. Tester une injection sur un site que tu n'administres pas est un délit, même sans intention malveillante et même si la faille est évidente.

Pourquoi ces deux failles sont incontournables

Une injection SQL permet de lire — parfois de modifier — la base de données d'un site en détournant une requête. Un XSS permet d'exécuter du JavaScript dans le navigateur d'un autre utilisateur. Les deux reposent sur la même erreur de conception : faire confiance à une donnée qui vient de l'extérieur.

C'est aussi pour cette raison que le sujet est enseigné : comprendre l'attaque est la seule façon de savoir écrire la correction.

Étape 1 — Monter un environnement isolé

La règle avant tout : une cible que tu possèdes. Crée une machine virtuelle, place l'interface réseau en host-only (pas de pont vers ton réseau réel), puis démarre une application volontairement vulnérable — DVWA dans cet exemple : 

docker run --rm -it -p 8080:80 vulnerables/web-dvwa

Ouvre http://localhost:8080, connecte-toi avec les identifiants par défaut, clique sur Create / Reset Database, puis règle DVWA Security sur low.

Pourquoi une VM : si l'application est vulnérable par conception, elle l'est aussi pour ton réseau. L'isolement n'est pas une précaution morale, c'est une mesure technique.

Étape 2 — Repérer un paramètre injectable

Une injection se cherche là où une valeur transite vers une requête. Ici, l'URL contient un paramètre id : 

http://localhost:8080/vulnerabilities/sqli/?id=1&Submit=Submit

Remplace la valeur par une apostrophe seule (id=1') et observe : un message d'erreur SQL apparaît. C'est le signal que l'entrée est concaténée directement dans la requête au lieu d'être traitée comme une valeur.

  • Réponse normale → entrée utilisée comme donnée.
  • Erreur SQL → entrée utilisée comme code.
  • Aucun changement → l'entrée est filtrée ou traitée autrement.

Étape 3 — Injection SQL : sortir du contexte

La requête serveur ressemble à ceci : la chaîne saisie est insérée telle quelle dans le WHERE. 

SELECT * FROM users WHERE id = '$id';

Ferme la chaîne, puis enchaîne sur un second SELECT dont le résultat sera affiché à la place des données attendues : 

1' UNION SELECT user, password FROM users --
  • 1' : ferme la chaîne de caractères du WHERE.
  • UNION SELECT : ajoute un jeu de résultats à celui de la requête.
  • -- : commente la fin de la requête d'origine.

Question 1 : que vois-tu apparaître dans la page ? Reconnais-tu la colonne password ? Le principe est illustré : la base ne demande pas si l'instruction était prévue, elle l'exécute.

Étape 4 — Contourner une authentification

Même mécanisme sur un formulaire de connexion : la requête de vérification ressemble à SELECT * FROM users WHERE user = '$u' AND password = '$p';. Une condition toujours vraie rend la vérification inutile : 

admin' --

L'apostrophe ferme la chaîne, le commentaire supprime le test du mot de passe — la requête ne cherche plus qu'un utilisateur existant. Question 2 : pourquoi aucune connaissance du mot de passe n'était-elle nécessaire ?

Étape 5 — Comprendre la cause dans le code

La faille ne vient pas de l'apostrophe, mais de la façon dont la requête est construite. Compare les deux approches : 

# ❌ Concaténation : l'entrée devient du code
query = "SELECT * FROM users WHERE id = '" + user_id + "'"

# ✅ Requête préparée : l'entrée reste une donnée
query = "SELECT * FROM users WHERE id = ?"
cursor.execute(query, (user_id,))

Dans le second cas, le moteur reçoit la requête et les valeurs séparément : une apostrophe ne peut plus modifier la structure de l'instruction. C'est la correction de fond, indépendante de la manière dont l'application affiche ses erreurs.

À retenir : masquer les messages d'erreur SQL est utile, mais ce n'est pas une correction. Une injection silencieuse reste exploitable — en aveugle, simplement plus lentement.

Étape 6 — XSS : réfléchi puis stocké

Le XSS ne s'attaque pas à la base de données mais au navigateur des visiteurs. Page XSS (reflected) de DVWA : saisis une valeur et vérifie si elle est renvoyée telle quelle dans la page. 

<script>alert(document.cookie)</script>

Si le mot-clé script est filtré mais que l'entrée n'est toujours pas encodée en sortie, la faille demeure — elle change simplement de forme : 

<img src=x onerror=alert(1)>

Page XSS (stored), même test dans un champ qui est enregistré (un commentaire) : la charge n'est plus renvoyée au seul visiteur qui l'a saisie, elle est servie à tous ceux qui consultent la page. C'est le passage d'un bug « désagréable » à un vol de session potentiel.

  • Réfléchi : la charge transite par la requête et la réponse.
  • Stocké : la charge est persistée puis servie à chaque visite.
  • Effet : lecture des cookies non protégés, action au nom de la victime.

Étape 7 — Corriger : défense en profondeur

Aucune de ces failles ne se referme avec un filtre de « mots interdits ». Il faut traiter la donnée au bon endroit :

  • Injection SQL : requêtes préparées avec paramètres liés, ou ORM. Jamais de requête construite par concaténation.
  • Validation d'entrée : un identifiant attendu numérique doit être converti en entier avant usage.
  • XSS : encoder la sortie selon son contexte d'affichage (HTML, attribut, JavaScript, URL) — et non se contenter de filtrer l'entrée.
  • Côté JavaScript : préférer textContent à innerHTML pour insérer des données non fiables.
  • Cookies : HttpOnly (inaccessible en JS), Secure et SameSite.
  • Content-Security-Policy : limiter les sources de scripts exécutables, ce qui réduit fortement l'impact d'un XSS résiduel.
  • Moindre privilège : le compte applicatif n'a besoin ni de DROP, ni d'accès aux tables inutiles.
Le vrai enseignement : injection SQL et XSS ont une cause commune — une donnée non fiable interprétée comme du code (SQL, HTML ou JavaScript). Le filtre d'entrée aide, mais la correction fiable est le traitement de la donnée à l'endroit où elle est utilisée.
⚠ Rappel : cet exercice n'a de sens que sur une application vulnérable que tu as installée toi-même. La reconnaissance, la lecture de données ou l'injection de script sur un service tiers sont des infractions pénales.

Synthèse du lab

Ce que tu as appris

  1. Isoler un environnement d'entraînement volontairement vulnérable.
  2. Repérer un paramètre injectable par le comportement de l'application.
  3. Détourner une requête SQL pour lire des données imprévues.
  4. Injecter du JavaScript côté client, en version réfléchie puis stockée.
  5. Corriger à la source avec des requêtes préparées et l'encodage de sortie.
  6. Durcir la réponse : cookies, CSP et moindre privilège.

Bonnes pratiques retenues

  • Toujours utiliser des requêtes préparées avec paramètres liés.
  • Ne jamais construire une requête en concaténant des chaînes.
  • Encoder la sortie selon son contexte d'affichage.
  • Ajouter une CSP stricte et des cookies HttpOnly.
  • Considérer toute entrée utilisateur comme non fiable, y compris la sienne.

Pour aller plus loin

  • Observe les requêtes du lab avec Wireshark.
